### Authenticated acceptance of preview d807e462

The new preview was Ready and the operator completed CRM login. Home, Customers, Follow-up and Customer Inbox loaded. The loaded script URL confirmed the audit build rather than the older production UI.

Acceptance uncovered additional blocking defects, now covered by a further code revision:

- All 17 historical applications still lacked usable IDs. The follow-up guards disabled their actions, but other application actions remained available. Do not treat the earlier header normalization as a completed repair of existing records.
- An empty application ID matched the first malformed application, then joined every blank-ID application into Customer 360. This could mix unrelated customer history. The new revision excludes malformed applications from identity joins and keeps valid same-phone lead history separate from unrelated customers.
- Generic backend updates could match the first blank-ID row, and scope sets included blank IDs. The new revision requires nonblank, unambiguous record identities before writes and removes blank IDs from authorization sets.
- Application creation could drop its generated identifier when the worksheet lacked the identifier header. Both creation paths need required identity headers and fail-closed append validation. This is a proven code failure mode, not yet a verified diagnosis of the original 17 rows.

The authenticated reply composer loaded **13 approved Meta templates**, including **3 image/document-header templates**. Selecting a local company-logo PNG automatically selected the approved image template and showed its exact text. The test was cancelled without sending. This verifies local file selection and template matching, not provider delivery or PDF upload.

Inbox Last contact values were unavailable on the inspected records. Missing per-message timestamps remain a data acceptance issue; do not invent dates from a lead's latest activity or claim the historical timeline is fully verified.

## Remaining acceptance gates

1. The two-profile identity preview acceptance passed as described above. The 17 historical missing IDs and unavailable inbox timestamps still require source-data investigation and controlled repair; a page loading successfully alone is insufficient. Inspect full raw headers/column positions and the exact affected rows first: current bounded readers can miss identifiers outside their range, while semantic header aliases are not resolved. The actual origin of all 17 malformed records is not yet established. Prepare a recoverable snapshot and row-by-row dry-run mapping before requesting repair approval.
2. Use an explicitly designated test customer to verify end-to-end WhatsApp text, approved image and PDF delivery, plus Meta delivered/read callbacks. Existing historical delivery records do not prove each new path works.
3. Complete a controlled SharePoint upload/read test with a synthetic file and verify customer/application folder isolation. No private document upload is part of this audit.
4. Review historical duplicate/malformed application data with a recoverable backup before consolidation. Do not silently delete or merge it by customer name.
5. LMS has no implemented vendor submission/decision adapter. Obtain the vendor contract and sandbox, implement the adapter, and verify receipts before enabling submissions. Environment flags cannot substitute for this work.
6. Sheets is not a transactional queue. Durable retry holds and in-process locks reduce duplicates, but strict exactly-once delivery across simultaneous serverless instances requires a transactional idempotency store. Do not advertise this as guaranteed.
7. Confirm live Notion build-sync output and resolve conflicting business-policy warnings with the owner. The checked-in snapshot is a fallback, not proof of a recent live sync.
