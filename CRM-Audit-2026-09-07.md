## Release boundary

This is evidence for Draft PR #84, not a declaration that production is defect-free. The live production site remains on the earlier main release until this PR is explicitly approved and merged. Automated checks exercise synthetic data and mocked providers; they do not send messages to customers, submit loans, or upload customer documents.

## Repairs and regression coverage

| --- | --- | --- |

## Browser and read-only checks

The authenticated previous PR #84 preview loaded the home, customer and follow-up workspaces. It showed 6 customers, 17 applications and 78 sent/queued records. These counts are observations, not clean-data guarantees. Several historical applications are duplicates, and follow-up action buttons had blank application identifiers. Header compatibility and fail-closed action handling are included in this audit's repairs; a newer preview must be checked after deployment.

Unauthenticated production checks returned the expected denial for CRM data and dispatch endpoints. Protected media without credentials was denied. The Petaling Jaya short map route redirected to its configured address; an unknown branch returned 404. No live records were changed by these checks.

## Remaining acceptance gates

1. Verify the newly deployed preview, including nonblank application action IDs, chronological customer history, the reply composer and role access. A page loading successfully alone is insufficient.
2. Use an explicitly designated test customer to verify end-to-end WhatsApp text, approved image and PDF delivery, plus Meta delivered/read callbacks. Existing historical delivery records do not prove each new path works.
3. Complete a controlled SharePoint upload/read test with a synthetic file and verify customer/application folder isolation. No private document upload is part of this audit.
4. Review historical duplicate/malformed application data with a recoverable backup before consolidation. Do not silently delete or merge it by customer name.
5. LMS has no implemented vendor submission/decision adapter. Obtain the vendor contract and sandbox, implement the adapter, and verify receipts before enabling submissions. Environment flags cannot substitute for this work.
6. Sheets is not a transactional queue. Durable retry holds and in-process locks reduce duplicates, but strict exactly-once delivery across simultaneous serverless instances requires a transactional idempotency store. Do not advertise this as guaranteed.
7. Confirm live Notion build-sync output and resolve conflicting business-policy warnings with the owner. The checked-in snapshot is a fallback, not proof of a recent live sync.

## Test safety and release procedure

Local result: **347 checks; 344 passed, 0 failed, 3 skipped**. The skipped checks require external Make scenario blueprints (exception assignment, Motor/Handphone isolation, and second-hand routing). Twenty application/API JavaScript files passed syntax checks. The local build completed using the explicit no-key Notion snapshot fallback; it did not perform a live Notion sync.

The first Vercel audit build successfully synced 19 Approved Notion pages (`notion-2026-09-07-bcfca67833ea`), then correctly stopped on a test affected by the deployment's model environment override. Test workers now clear service configuration and credentials before installing explicit fixtures, in addition to blocking live fetch. This does not change the deployed application's model or service settings.

Run `npm test` and `npm run build`. The local build may explicitly keep its checked-in Notion snapshot if no key is configured; record that limitation. Vercel runs `npm run build && npm test`. Tests may install explicit provider mocks, but unmocked fetch calls are blocked even when the deployment has real credentials.

Keep the PR in Draft until code review and the applicable acceptance gates are understood. Distinguish PREPARED, QUEUED, PROVIDER_ACCEPTED, DELIVERED, VERIFIED and SUBMITTED; never describe one as another.
