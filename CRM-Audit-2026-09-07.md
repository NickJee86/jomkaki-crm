## Remaining acceptance gates

### Second-pass source and workflow findings

Read-only Google Sheets inspection of the Operations Hub established actual schema damage, not just a suspected range limit: Applications A1 is `pplication ID`, Message_Outbox A1 is `utbox ID`, Document_Log A1 is `ocument ID`, Conversation_State A1 is `tate ID`, and Event_Registry A1 is `vent ID`. Applications A1:C25 contains 17 records with blank first-column IDs; Message_Outbox A1:B100 contains 78 records with blank first-column IDs. No historical IDs were recovered or fabricated. Inbox A1 is `eceived At`, but AD1 already contains the correct `Received At`; renaming A1 to the same label would create a duplicate and is not the proposed repair.

The second code pass removes fixed row/column truncation for an explicit allowlist of operational tables while leaving user-access and system-config reads unchanged. Actual schema examples are Leads follow-up fields at AQ:AW, canonical Inbox time/handover fields at AD:AE, and Motor Pricing workflow approval fields at AA:AM. Complete reads cannot recover an empty source cell. Source header correction requires backup and approval; it has not been performed.

Read-only catalog/price comparison explains the 61 gaps: 16 motor specifications have existing amounts in inactive/unapproved rates; 18 motor specifications have no matching price row; 27 phone specifications have inactive empty rates. Do not auto-approve or activate these prices. This classification distinguishes formatted RM amounts from blanks.

Additional code defects reproduced and corrected in this pass:

- Application quotes now enforce active publication, workflow approval and effective-date boundaries in addition to exact SKU identity.
- Changing the reply-composer customer clears the previous private draft and attachment. Submission snapshots the entire recipient/message payload before asynchronous file reading, prevents duplicate submits and recovers controls after failure; it does not close a later replacement dialog.
- Same-customer application reuse preserves the application's canonical lead association before conversation lookup. Missing/ambiguous/conflicting identities fail closed; new-customer absence remains absent so lead creation still runs. Current-application document checks cannot borrow another application's verified income/identity/consent files.

These are synthetic behavioral and read-only source checks. No actual customer messages, document uploads, quote approvals or original sheet changes were made.

1. The two-profile identity preview acceptance passed as described above. Source inspection confirmed damaged headers and genuinely empty identifier cells as detailed above. The historical record-link repair still requires a recoverable snapshot and row-by-row mapping; who or what originally truncated the headers is not established. Do not silently infer IDs from customer name, phone, model or Lead ID.
2. Use an explicitly designated test customer to verify end-to-end WhatsApp text, approved image and PDF delivery, plus Meta delivered/read callbacks. Existing historical delivery records do not prove each new path works.
3. Complete a controlled SharePoint upload/read test with a synthetic file and verify customer/application folder isolation. No private document upload is part of this audit.
4. Review historical duplicate/malformed application data with a recoverable backup before consolidation. Do not silently delete or merge it by customer name.
5. LMS has no implemented vendor submission/decision adapter. Obtain the vendor contract and sandbox, implement the adapter, and verify receipts before enabling submissions. Environment flags cannot substitute for this work.
6. Sheets is not a transactional queue. Durable retry holds and in-process locks reduce duplicates, but strict exactly-once delivery across simultaneous serverless instances requires a transactional idempotency store. Do not advertise this as guaranteed.
7. Confirm live Notion build-sync output and resolve conflicting business-policy warnings with the owner. The checked-in snapshot is a fallback, not proof of a recent live sync.
